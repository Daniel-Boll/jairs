# ADR-0148: `#simd` — a vector type, at the width the hardware actually has

- **Status:** Accepted
- **Date:** 2026-09-01
- **Deciders:** dboll
- **W8 sub-wave 7.** §2.1 lists "SIMD vectors" in this wave's content and PLAN §7 named the fork to
  settle first: *are they types or layout attributes?* This ADR answers that, and two other questions
  that only appeared once the premise was probed.
- No design fork was put to the decider; the recommended approach was taken and the rejected
  alternatives are recorded below, per the session directive.

## Context

### Probed before writing, and it changed the design twice

`AGENTS.md` names the habit — confirm a wave's premise by *writing* the thing before planning around
it. It has now paid off seven times (ADR-0067 §0, ADR-0070 §0, ADR-0072 §5, ADR-0073 §0, ADR-0075's
closing claim, ADR-0140's dump, ADR-0147's three findings). This is the eighth, and the two facts it
found are the two that shape the whole feature. Both were found by compiling Cranelift IR directly,
for the host triple `aarch64-apple-darwin`, through the same ISA construction `jr-codegen-clif` uses.

**Fact one: a vector operation compiles at exactly 128 bits, and nowhere else.** The type
*constructor* is happy to make anything — `types::I64.by(4)` returns `I64X4` and reports 256 bits — so
a plan built on the constructor would have looked fine right up to the first compile:

```
I64X2: iadd COMPILES
I64X4: iadd FAILS -> Unsupported("Unexpected SSA-value type: i64x4")
I32X4: iadd COMPILES
I32X8: iadd FAILS -> Unsupported("Unexpected SSA-value type: i32x8")
```

So the set of vector types this language can have is not a matter of taste. It is the six shapes a
128-bit register holds: `[[16]]s8`, `[[8]]s16`, `[[4]]s32`, `[[2]]s64`, `[[4]]float32`,
`[[2]]float64`, and their unsigned integer counterparts.

**Fact two: integer division is not a vector operation.** Cranelift's verifier refuses `sdiv` and
`udiv` on every lane count, at every width:

```
[[4]]s32 iadd: OK    [[4]]s32 imul: OK    [[4]]s32 sdiv: NO (verifier)
[[4]]f32 fadd: OK    [[4]]f32 fmul: OK    [[4]]f32 fdiv: OK
```

That is not a Cranelift gap to work around — it is the hardware. Neither SSE nor NEON has an integer
vector divide. So the operator set differs *by element type*: `+ - *` for an integer vector, and
`+ - * /` for a float one.

### What a vector actually is, which is what settles PLAN §7's fork

The fork was "types or layout attributes", and the probe answers it in a way neither option quite
anticipated: **a vector's layout is identical to the array's, and only its *operations* differ.** A
4×`s32` vector is sixteen contiguous bytes, exactly like `[4]s32`. What `[4]s32` cannot do is `a + b`.

Both halves of that matter, and they pull in opposite directions:

- Because the *layout* is the array's, a separate type constructor with its own layout rules would be
  duplicating a computation this project has already centralised once, deliberately (ADR-0018 §2).
- Because the *operations* differ, the two cannot be the same type. If `#simd [4]s32` and `[4]s32`
  were one pool item, `a + b` would be legal on both, and "which of these two arrays is a vector" is
  not a question a compiler can answer from a use site.

## Decision

### 1. The syntax is an attribute; the type is its own pool item

`v: #simd [4]s32;` — the attribute sits before an array type, in the position `#align`/`#place`
established one sub-wave earlier for the same reason (ADR-0144 §1): it is a *property of the storage*
being declared, read left-to-right before what is stored.

But `jr-pool` gains `Item::VectorType { elem, lanes }`, distinct from `ArrayType`. The syntax says
"an array, but vector", and the type system says "a different type with the same layout", because
those are two different questions and only the second one has to be exhaustive.

**This is the opposite call to ADR-0147 §1's**, which refused an `Item::SoaType` on the grounds that
every match on `Item` across five crates would grow to say "the same as a struct". The two are
consistent for a stateable reason, and it is the whole test for whether a new `Item` is warranted:

> An `#soa` struct answers every question the same way an ordinary struct does — its fields have
> types, offsets, and a layout, and after resolution nothing about it is special. A vector answers
> three questions **differently**: its representation is a register rather than memory
> (`jr-codegen-clif`'s `Repr`), an arithmetic operator applies to it (`jr-sema`), and its element
> count is fixed by its width rather than chosen (§2). A new `Item` earns its five matches exactly
> when the arms would differ, and here they do.

**Rejected: `simd(4, s32)`**, a parameterised-struct-shaped spelling. It collides with ADR-0085 §3's
`Name(args)` form, which resolves to a *declared* parameterised struct — so `simd` would have to
become a name the resolver knows about but no file declares, which is the "builtin that looks like a
declaration" trap E0269 exists to keep out.

**Rejected: `[[N]]T`.** It reads as an array of arrays, which is a real type this language will
eventually have, and the two would be one token apart.

**Rejected: making it an ordinary array and gating the operators on a `#simd` *variable* attribute.**
Then the vector-ness lives on the declaration rather than the type, so it cannot survive being passed
to a procedure, returned, or stored in a struct — and a feature whose entire purpose is arithmetic
would not compose with the one construct that arithmetic lives in.

### 2. The legal widths are exactly the ones the hardware has, and the refusal says so

Total width must be exactly **16 bytes**, and the element must be a numeric scalar. That gives ten
types (four signed, four unsigned, two float). Anything else is **E0285**, and the message names the
six shapes rather than stating a rule, because "16 bytes" is the *reason* and the shapes are the
*answer*:

```
error[E0285]: `#simd` needs a vector exactly 16 bytes wide, and `[4]s64` is 32
  = a vector is one machine register: 16×s8, 8×s16, 4×s32, 2×s64, 4×float32, or 2×float64
  = write `[[2]]s64`, or use a plain `[4]s64` array if you want storage rather than arithmetic
```

**This is deliberately a machine fact in the language**, and it is the one place in this project where
that is the correct trade. A vector type exists *because* the machine has vector registers; a
portable-looking `#simd [8]s64` that silently became four registers, or worse a loop, would be a type
whose whole purpose the compiler had quietly declined to serve. ADR-0058 §3's rule — a directive that
is silently ignored is worse than one that is rejected — applies with unusual force here.

**Rejected: any N, with the back end splitting wide vectors into register-sized pieces.** That is
vector legalisation, which is a real pass with a real spec, and writing one in `jr-codegen-clif`
would put a mid-end responsibility in a back end — the exact split ADR-0017 §1 drew. LLVM would do it
for free and Cranelift cannot, so the two engines would differ in *how much* they legalise, and the
differential harness would be comparing two different programs.

**Rejected: any N, lowered elementwise everywhere.** Then `#simd` is a type with no machine meaning,
and this project cannot even measure whether it helped (ADR-0146 §4) — so it would be a promise with
neither an implementation nor a test behind it.

### 3. Integer `/` on a vector is refused, not scalarised

E0285 again — one code for "this is not how a vector is used", the way ADR-0147 §2 kept `#soa`'s three
refusals together:

```
error[E0285]: `/` is not a vector operation on integers
  = no machine has an integer vector divide; only float vectors can be divided
  = divide the lanes individually, or use a float vector
```

**Rejected: scalarising it** — emitting a loop that divides each lane. It would compile, produce the
right answer, and be *slower than the scalar code it replaced*, invisibly, in the one construct a
reader chose specifically for speed. A silent pessimisation is the performance-domain twin of a silent
miscompile, and this project refuses those on principle rather than case by case.

### 4. The VM loops, and that is what the differential is for

`jr-vm` has no vector registers and will not grow any: it is a bytecode interpreter whose `Value` is
one scalar. A vector lives in memory as its layout says, and an elementwise operation is a loop over
the lanes.

So the two engines execute *genuinely different* code for the same MIR — a loop against one
instruction — which is the first time in this project that has been true of an arithmetic operator.
That is exactly what the three-way differential exists to hold together, and it is a stronger test
here than anywhere it has been applied so far: integer wrap-around, float rounding, and lane order all
have to agree byte for byte across a loop, a NEON instruction, and whatever LLVM picks.

### 6. An integer vector takes the *wrapping* operators, and only those

Found while building, not while planning, and it is the sharpest decision in the wave.

A scalar `+` traps on overflow (ADR-0002). **No vector add can trap**: no target has a per-lane
overflow flag, and Cranelift's `iadd` on a vector wraps silently. So the VM — which loops, and
therefore *could* trap per lane — and the two native engines can only be made to agree on wrapping.

Three ways out, and the third is taken:

1. **Let `+` wrap on a vector.** One spelling would then mean two things depending on the operand
   type, silently. That is the class of difference this project refuses on principle rather than case
   by case, and a reader porting scalar code to vectors would get a different answer with no signal.
2. **Make `+` trap.** Every lane needs a compare and a branch. That destroys the entire reason the
   construct exists, and it does so invisibly — the §3 argument against scalarising a divide, applied
   to the operator people will actually reach for.
3. **Require the operators that say they wrap.** `+% -% *%` are already in the language, put there by
   ADR-0002 as the documented opt-out from trapping. A program gets the arithmetic it asked for, the
   three engines agree, and nothing about scalar arithmetic changes.

`+ - *` on an integer vector are therefore E0285, and the message names the wrapping spelling. A
**float** vector keeps `+ - * /`, because a float never traps in the first place (ADR-0040 §1), so
there is no second meaning to distinguish and no reason to demand a second spelling.

### 5. What this wave does not do, named rather than implied

- **No comparisons.** `a < b` on vectors produces a *mask*, which is a second type with its own
  operations (`any`, `all`, `select`), and blending on a mask is the point of having one. That is its
  own wave, not a corner of this one.
- **No swizzles or shuffles.** They need a compile-time lane-index list, which is a const-eval
  question in a new place (ADR-0080 §3's `Code`-value question rewritten for integers).
- **No `#simd` on a dynamic array or a view.** A vector's width is its identity, and neither carries
  one.
- **No claim about speed.** ADR-0146 §4 stands: this project measures its own compile throughput and
  nothing about the programs it compiles. What is asserted here is *semantics* — that the three
  engines agree — and the register width is chosen so that the semantics are the machine's.

## Consequences

- **`jr-pool` gains an `Item`**, so every exhaustive match on one grows an arm. That is the cost the
  §1 test above says is worth paying, and it is paid once.
- **A new diagnostic code, E0285**, covering the width refusal, the element-type refusal, and integer
  division — one code for one construct's ways of being misused.
- **`jr-vm` gains an elementwise loop** for vector arithmetic, and `jr-codegen-clif` and
  `jr-codegen-llvm` each gain a `Repr` case that is a register rather than memory.
- **The differential harness gets its hardest case yet**: an operator where the VM and the native
  engines do not merely lower the same shape differently, but execute a different *number* of
  operations. `valid/119` exits 170 in all three, and the lane that carries the claim is
  `S32_MAX +% 1`: a saturating engine would answer 1 there and a trapping one would not finish.

### What building it found

Seven things, in the order they appeared. The first two are the probe's and are in the Context above;
these are the rest.

- **A vector is not register-representable in MIR, even though it is one machine register.** That
  predicate decides whether a local may be promoted to an SSA value, and an SSA value is a `jr-vm`
  `Value` — one scalar. A promoted vector local would have nowhere to live in the engine that has to
  agree with the other two, so a vector stays in a slot and the *back ends* hold the register.
- **Lane access needed no lowering at all.** `array_len` and `array_elem` in `jr-mir` answer for a
  vector, and everything downstream — the stride, the bounds check, the `for` bounds, the `.count`
  fold — was already right, because the layouts are identical. Before that, answering `None` refused
  every body that read a lane, through `give_up` rather than a placeholder, exactly as ADR-0017 §4
  requires. This is the strongest evidence that §1's "same layout, different operations" reading is
  the right one.
- **The lane-type dispatch has to come before the scalar float check, in both back ends.**
  `FloatKind::of` answers `None` for a vector of floats, so a `#simd [2]float64` fell through to the
  *integer* path and emitted `iadd.f64x2`. Cranelift's verifier met that with `unreachable!()` — a
  **panic**, not the hard failure the existing comment there promises. LLVM's `into_int_value()`
  panicked the same way. One type wider than ADR-0040's original hazard, and the same fix.
- **`TYPE_START` was missing the directive token**, so `v: #simd [4]s32` reported "expected a type
  after `:`" at the `#`. The fourth recorded instance of that token-set trap; ADR-0045 found the set
  missing three keywords.
- **`is_type_kind` in `jr-fmt` was missing it too**, and the symptom was the one its own comment names
  as the reason it exists: `v: #simd [4]s32;` formatted to `v: ;`.
- **`.count` did not work until sema was told**, though MIR was already ready. Found by *writing* the
  corpus file, which asserted it before it was true — and a vector shares `ReceiverKind::Array`,
  because that variant's meaning is precisely "the count is a constant from the type".
- **`size_of(#simd [4]s32)` does not parse**, and that is not a gap this wave opened: a *structural*
  type argument does not parse at all — `type_info([4]s64)` does not either — which is ADR-0071 §5's
  fixpoint, deferred since W5. The corpus file records it rather than working around it.

Two of the corpus file's own arithmetic comments were **wrong** when first written, and the engines
were right: the `*%` term summed lanes the program does not read, and the float term used `g - f`
values from the wrong subtraction. Corrected in the file rather than by adjusting the expected exit
code, which is the only order that keeps a checksum meaningful.
