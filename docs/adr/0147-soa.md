# ADR-0147: `#soa` — a struct stored as arrays, with the access that makes it worth having

- **Status:** Accepted
- **Date:** 2026-09-01
- **Deciders:** dboll
- **W8 sub-wave 6.** §2.1 lists `#soa` in this wave's content. It is the last of the wave's
  *language* items; SIMD and parallel compilation are what remain after it.
- No design fork was put to the decider; the recommended approach was taken and the rejected
  alternatives are recorded below, per the session directive.

## Context

### What structure-of-arrays is for, and why a language rather than a library provides it

An array of structs interleaves fields: `[N]Entity` puts every `Entity`'s position next to its own
hit points. A loop that reads only positions therefore pulls hit points into cache and discards them,
and cannot be vectorised over positions at all because they are `sizeof(Entity)` apart. A
structure-of-arrays layout — one array per field — makes that loop contiguous.

The transformation is mechanical, which is exactly why a language should do it: writing it by hand
means declaring the element type once per field, keeping the count in step across all of them, and
changing every access site if the layout is ever reversed. Jai provides `SOA` for this reason.

### The measurement this wave took says where the win is not

ADR-0146's number says `build` costs 4.4× `check`. So this is not a compile-time optimisation and is
not being sold as one: `#soa` changes the *program's* memory layout, and this project has no way to
measure a program's speed (ADR-0146 §4 declined to add a clock). What it can measure is that the
layout is what was asked for — which is what the corpus file does, through `size_of` and offsets.

### Why the access sugar is not separable

The obvious staging — layout first, `e[i].x` sugar later, as ADR-0138 split the variadic surface from
its packing — was considered and refused. Without the sugar, `#soa(N)` buys almost nothing over
writing `pos: [N]Vector3;` by hand: the count can already be a named constant, so the only thing
gained is a keyword. The sugar *is* the feature, so it is in the wave.

## Decision

### 1. `#soa(N)` is a struct attribute; each field's type becomes `[N]T`

```jr
Entities :: struct #soa(4) {
    x: s64;
    hp: u8;
}
```

lays out as `{ x: [4]s64, hp: [4]u8 }`. `N` is an integer literal or a literal-valued constant,
through `named_constant_int` — its **fourth** caller, and again needing no change to serve one
(ADR-0070 wrote it, ADR-0129 generalised it, ADR-0144 §2 was the third).

The attribute goes on the `struct` keyword's node, with its own `SyntaxKind` (`SOA_ATTR`), following
the precedent that gives each attribute a kind rather than sharing one that carries its directive
text: a downstream match on kinds is exhaustive where a match on strings is not.

**The field's declared type is what gets wrapped, not a new kind of field.** `jr-sema` resolves
`x: s64` and then interns `[4]s64` as the field's type, so every consumer downstream — layout, field
offsets, `type_info`, both back ends, the VM — sees an ordinary struct of arrays and needed no
change. That is the same leverage ADR-0144 got from putting placements in the layout fold, one level
up: here the transformation happens *before* layout rather than inside it.

**Rejected: a distinct `Item::SoaType`.** It would make every match on `Item` grow, in five crates,
to say "the same as a struct". The interesting property of `#soa` is that after resolution there is
nothing special about the type.

**Rejected: `#soa` with no count, sized by a runtime length.** That is a different feature — a
struct of *views* or of dynamic arrays, with an invariant that all the counts agree — and it needs a
decision about who maintains that invariant. A fixed `N` has no invariant to maintain.

### 2. `e[i].x` means `e.x[i]`, and sema records the rewrite for MIR

Indexing an `#soa` struct is legal **only** as the receiver of a field access. `e[i].x` types as the
field's element type and lowers to `Field(x)` then `Index(i)` — the same place MIR would build for
`e.x[i]`.

**Sema decides and MIR reads**, through a `soa_fields` entry keyed on the field expression, exactly as
`operator_calls`, `type_info_calls`, `any_calls` and `variadic_calls` already are. The alternative —
each of the two crates recognising the pattern itself — is the "two searches for the same thing are
two chances to disagree" trap this project keeps recording, and here a disagreement is a *wrong
address*: sema would type the expression as an element while MIR read a whole array.

**Why the field access and not the index expression carries the entry.** The index expression alone
is not enough information: `e[i]` has no type of its own in this design, so recording against it
would need a placeholder type for something the language refuses to let exist. Recording against the
`Field` — where both the index and the field name are in reach — means the refusal below is what
happens to every *other* use.

**An `#soa` index anywhere else is E0284.** `e[i]` as a value, an argument, an assignment target
without a field, or the receiver of anything but a field access: all refused, because there is no
type for it. Jai's answer is a synthesised struct-of-pointers, which is a real design and a much
larger one — it needs a type that exists only as an intermediate, and pointers into N arrays kept
consistent. Refusing is honest and leaves that available.

**`e.x[i]` keeps working**, unchanged and unrewritten: the field is genuinely an array, so this is an
ordinary array index. That matters more than it looks — it means the sugar is *sugar*, and a reader
who does not know about it can still read every program.

### 3. `#soa` does not compose with `using`, and says so

A `using` field on an `#soa` struct is refused (E0284). `using` promotes a field's own fields into the
enclosing struct for *lookup* (ADR-0050 §1), and under `#soa` the field is an array — so the promoted
names would have to mean "the array of that subfield", which is a second transformation stacked on
the first with no obvious spelling for the index. Refused rather than guessed.

## Consequences

- **One new diagnostic code, E0284**, covering every misuse of an `#soa` type: an index that is not a
  field receiver, and a `using` field. One code because each is "this is not how an `#soa` struct is
  used" and the *message* says which, the reasoning E0129, E0130 and E0282 already use. **E0285 is
  the first free code.**
- **`jr-fmt` needs the attribute**, and the formatter has lost a construct in most of the waves that
  added one. A test asserts survival *and* canonicalisation.
- **The tree-sitter grammar needs it**, with gate 6 catching a missing literal token as an ERROR node.
- **No engine changed, again.** The type is an ordinary struct of arrays after resolution, and the
  access lowers to an ordinary place. `valid/118` asserts the layout through `size_of` and the access
  through values, in all three engines.
- **Deliberately not done, and named**: a synthesised element type so `e[i]` can be a value (§2), a
  count-free `#soa` over views or dynamic arrays (§1), `using` inside an `#soa` struct (§3), and any
  claim about *program* speed — this project cannot measure one (ADR-0146 §4).

### Three things building it found

- **The `#soa` predicate had to go in the pool, not the HIR.** `jr-sema` asks "is this an `#soa`
  struct" about a type that may have been declared in another file (ADR-0117), and the pool is the one
  place every file's declarations already meet — so `soa_counts` is a `DeclId`-keyed side table beside
  `struct_fields`, recorded where the fields are and for the same reason. Two lookups, one per file's
  HIR, would have been two chances to disagree about a type's identity.
- **An expression id indexes a *body*'s arena, not the file's.** The first version of both hooks read
  `hir.exprs` directly, which is the top-level arena — so the sugar silently did nothing inside a
  procedure, which is everywhere it is used. That is what `ExprScope` exists for, and both sites now
  go through the scope-aware accessor.
- **`e[i]` needs a recorded type even though it has none.** `jr-mir`'s `scan` refuses a body holding
  a reachable expression typed `PoolId::ERROR`, so recording poison for the index expression refused
  every program that used the sugar. It is recorded with the *receiver's* type instead: an `#soa`
  index is a projection step rather than a value, nothing reads the entry, and §2's refusal is what
  keeps any other use from observing it.
