# ADR-0076: `Any` is a `{type, pointer}` pair, and a pointer converts only where a type is erased

- **Status:** Accepted
- **Date:** 2026-08-03
- **Deciders:** dboll
- **W4 sub-wave 8.** ADR-0075 delivered `type_info(T)` and named `Any` as the second half of RTTI,
  "a `{type, pointer}` pair, plus rules for what may go in one and how it is read back". Probing found the
  pair is already representable and the *rules* are the whole problem — §0.

## Context

### 0. What running found

`Any` erases a value's type, so it needs to hold a pointer to a value of **any** type in one field. Built
by hand, that works:

```
Boxed :: struct { info: *Type_Info; data: *u8; }
n: u8;  n = 7;
ti := type_info(u8);
b: Boxed;  b.info = *ti;  b.data = *n;
exit(cast(s64, b.data.*) + b.info.size);   // 8 — the value 7 plus u8's size 1
```

And for anything that is not already a `u8` it does not, because the erasure step is refused:

```
p: Point;
b.data = cast(*u8, *p);   // error[E0232]: cannot cast `*Point` to `*u8`
```

Five facts, each checked rather than assumed:

- **The `{*Type_Info, *u8}` pair needs nothing new.** The program above runs and exits 8. `*Type_Info`
  works because ADR-0075 returns a `Type_Info` by value and `*i` takes its address like any local's.
- **The blocker is a *conversion*, not a representation.** `cast` covers int→int, int→float, float→int,
  float→float and enum→numeric. A pointer is in none of them.
- **That refusal is not a recorded decision.** ADR-0037, which introduced `cast`, does not mention
  pointers **at all** — grep finds no occurrence. The refusal lives in a code comment ("refused here rather
  than becoming pointer arithmetic by the back door"), which is a good instinct rather than a decided
  position. So this ADR decides something *undecided*; it does not overturn an ADR.
- **A pointer's layout does not depend on its pointee.** `layout_of` answers
  `{size: pointer_size, align: pointer_align}` for every `Item::PointerType(_)`, uniformly. So an erased
  pointer is representationally **honest**: nothing is reinterpreted, truncated or padded, and the
  conversion emits no code at all.
- **`Any` is not spellable yet** — `a: Any` reports E0212, the same way `Type_Info` did before ADR-0075 §2
  declared it in `modules/Basic`.

The last two together are what shape §1: because the conversion has no *runtime* content, the entire
question is which conversions the type system should permit, and that is a question about what a reader can
be sure of rather than about what the machine does.

## Decision

### 1. A pointer converts to `*u8` **implicitly, and only when a type is being erased**

There is no general pointer cast. Instead, `*T` coerces to `*u8` in exactly one position: an argument
being converted to `Any`. `any_of(p)` — and passing a `*T` where an `Any` is expected — erases; a bare
`cast(*u8, p)` stays E0232.

**Why not a general `cast(*u8, p)`**, which is the obvious answer and what C would do. Two reasons, and the
second is the one that decides it:

- It makes every pointer type interconvertible, so `cast(*Point, q)` for an unrelated `q` becomes legal and
  a wrong pointee type is a **silent wrong read** rather than an error. That is precisely the
  reinterpretation ADR-0045 §1 confined to `union`, where a programmer writes the union and can see it.
  Pointer casts would put the same hazard on every pointer in the language, unmarked.
- The erasure `Any` needs is not a general conversion. It is one step of one operation, and the *inverse*
  step is where the type must be recovered — which §2 gives a checked form. A general cast would supply the
  forward direction and leave the reverse unchecked, which is the worst split: easy to write, impossible to
  verify.

**Why implicit rather than an explicit `xx`.** ADR-0046 made `xx` the marker for "the context supplies what
the source omits", and this *is* that shape — but an `Any` parameter is already a declaration that the
callee does not know the type. Requiring `xx` at every call would mark the conversion twice and read as
though something lossy happened; nothing is lost, because the type travels in the other field. This is the
same argument ADR-0057 used for the context parameter being implicit: a thing that always happens at a
known boundary is not informative to spell.

**Rejected: a `reinterpret` or `transmute` keyword.** Honest and general, and it is a *bigger* feature than
`Any` needs — it would have to answer what happens between types of different sizes, which is a decision
with no user waiting for it. `Any` needs one direction of one conversion, and §2 needs one checked read;
neither wants a general escape hatch, and adding one now would make the checked read optional in practice.

### 2. Reading an `Any` back is **checked against its type**, and refuses on mismatch

`any_as(a, T)` returns the value when `a.type` describes `T` and **traps** otherwise. It is not a cast: the
whole point of carrying the type is that the read can verify it, and a read that ignored `a.type` would
make `Any` a `void*` with extra steps.

**A trap rather than a returned `bool` or an optional**, matching ADR-0068's `variant`: reading the wrong
case of a tagged value traps there, and `Any` is the same shape one level up — a tag and a payload, where
the tag says which read is valid. Two spellings of "the tag said no" would be two things to keep
consistent. A program that wants to *ask* compares `a.type` itself, which is an ordinary comparison of
`*Type_Info` values.

**The comparison is by described type, not by pointer identity.** ADR-0075 §4 declined to promise that two
`type_info(T)` calls yield the same pointer, so `any_as` compares what the `Type_Info` *says* rather than
where it lives. This is why §3 keeps `Any`'s type field a `*Type_Info` rather than an opaque handle: the
check needs to read it.

### 3. `Any` is declared in `modules/Basic`, beside `Type_Info`

```
Any :: struct {
    type: *Type_Info;
    data: *u8;
}
```

For ADR-0075 §2's reason, unchanged and now load-bearing twice: a type the compiler knows about must be
declared in Jairs if a program has to *name* it, because no compiler-declared type is spellable. `Any`
plainly has to be nameable — `takes :: (a: Any)` is the whole use case — so it goes where `Type_Info` went,
validated on lookup by the same mechanism (E0265 gains a second client).

**Rejected: `Any` as a compiler-declared structural type.** Symmetric with `Context`, and unspellable, so a
program could receive one and not declare a parameter of that type. The argument is ADR-0075 §2's and it
applies unchanged.

### 4. What is deliberately absent

- **Every value coercing to `Any` implicitly at any binding**, e.g. `a: Any = 3;`. A literal has no address
  to point at, so it would need a compiler-materialised temporary whose lifetime is a decision of its own
  (the storage question ADR-0075 §2 already declined once). §1's erasure applies to a *pointer*, so the
  caller decides what is pointed at and its lifetime is visible in the source.
- **An `Any` in a compile-time constant.** `V :: any_of(*p);` would intern a pointer, which has no
  compile-time value at all — the same reason ADR-0074 §2 keeps `string` out of `AggregateValue`.
- **Per-kind detail in `Type_Info`** (ADR-0075 §3), still owed and still a memory-ownership decision. `Any`
  does not need it: the type field answers "which type", and a program that wants a struct's fields needs
  the thing ADR-0075 deferred.
- **A general pointer cast** (§1), and **`transmute`** (§1).

## Consequences

- **E0232's documentation stops being the place a language decision lives.** The comment claiming a pointer
  cast is refused "rather than becoming pointer arithmetic by the back door" was doing the work of an ADR;
  §1 makes the position explicit and narrows it to the one conversion that has a reason.
- **A second client for `Type_Info`'s validation.** The `Basic` lookup and E0265 now serve two types, which
  is the first evidence that ADR-0075 §2's mechanism generalises rather than being a one-off.
- **A new trap kind.** `any_as` on a mismatch joins the divide-by-zero, bounds and wrong-variant traps, and
  must report a source location and a backtrace like the rest (ADR-0066) — a trap that could not say where
  it happened would be worse than the E0230 it replaces.
- **The erasure emits no code**, because a pointer's layout is pointee-independent (§0). So the two engines
  cannot disagree about it, and the differential's job is the *checked read* rather than the conversion.
- **This does not complete W4.** `#code`/`Code`, per-kind `Type_Info` detail and a cross-file `#run` value
  all remain, and the plan should say so rather than repeating ADR-0074's mistake of declaring the path
  clear.
