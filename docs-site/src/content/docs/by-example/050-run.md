`#run` evaluates an arbitrary expression at compile time in the bytecode VM. The result is
interned as a compile-time value — indistinguishable, afterwards, from a literal you had typed
by hand. It works both at file scope and inside a procedure body.

## At file scope

```jr
// `#run` evaluates an arbitrary expression at compile time in the bytecode
// VM. The result is interned as a compile-time value, indistinguishable
// from a literal.
COMPUTED :: #run add(2, 3);

add :: (a: s64, b: s64) -> s64 {
    return a + b;
}

// `#run` may also appear as a top-level statement, in which case it is
// executed for its side effects during compilation.
#run report();

report :: () {
}

main :: () {
    // Constant-folded before codegen ever sees it.
    total := COMPUTED + 1;
}
```

`COMPUTED :: #run add(2, 3)` runs `add` in the compile-time interpreter and binds the constant
`5`. By the time code generation sees `COMPUTED + 1`, there is no call left — only a folded
literal. A bare `#run report();` as a top-level statement runs purely for its compile-time side
effects.

## Inside a body

`#run` is not restricted to file-level constants. It may appear inside a procedure body, where
each occurrence computes its own value at compile time and the body carries the result:

```jr
main :: () {
    n := 0;

    // The simplest case: a value computed while compiling.
    a := #run add(2, 3);
    if a == 5 {
        n = n + 1;
    }

    // A second `#run` in the same body gets its own value — they are keyed by expression, so
    // two in one body cannot collide.
    b := #run add(4, 4);
    if b == 8 {
        n = n + 2;
    }

    // A loop in the callee.
    c := #run sum_to(5);
    if c == 10 {
        n = n + 4;
    }

    // Nested calls and arithmetic around the call.
    d := #run add(add(1, 2), 3) * 2;
    if d == 12 {
        n = n + 8;
    }

    // The file-scope constant, so this file proves the two kinds coexist.
    if FILE_LEVEL == 30 {
        n = n + 16;
    }

    // Every assertion: 31.
    if n == 31 {
        exit(0);
    }
    exit(1);
}
```

### Why a body `#run` is not just a call

The key idea (ADR-0069) is that a body `#run` **computes at compile time and the body contains
the result** — it is *not* a call the body performs at run time. The compiler collects body-level
`#run`s the same way it collects file-level ones, in one round-robin evaluation behind one cycle
detector, because two separate mechanisms evaluating `#run` would be two chances to disagree
about what a `#run` means.

Each `#run` is keyed by its expression, so two of them in one body — `a` and `b` above — get
independent values and cannot collide. The callee may loop (`sum_to`), and arithmetic and nested
calls around the `#run` fold too (`d`).

### Observing the result with `exit`

The `n` accumulator gives every assertion teeth. Each check that passes adds a distinct power of
two, so the final `exit` value encodes exactly which assertions held — here `31` means all five
passed. This is how the two engines (`jr run` and `jr build`) can be asserted to agree
byte-for-byte on the outcome: there is no compile-time call left in the MIR for them to disagree
about, because both receive the same interned constant.

### What a `#run` may not do

The rules are the same in a body as at file scope (ADR-0069 §3). A `#foreign` call is refused,
and a call that omits a defaulted argument is refused because const-eval runs before the phase
that would fill the default in. The *position* of a `#run` changed when bodies gained the feature;
the rules did not.
